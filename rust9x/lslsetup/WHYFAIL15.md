# WHYFAIL15 — The fix was in `bin/`, but every shipped exe embedded the old copy

Asked 2026-10-01, right after fixing the missing kitty panel icon: *"Can you fix
`/mnt/c/GitHub/.../lslsetup/` to output the correct stick too?"*

Short answer: **`lslsetup`'s embedded copy of `bin/lsl-pin-favorites` was
stale, and nothing was watching.** `include_str!` makes a *rebuild* pick up an
edit; it does nothing about a binary that was built earlier and is still the
one being shipped. Every `lslsetup.exe` on this box — `target/debug`,
`target/i586-rust9x-windows-msvc/{debug,release}`, and
`dist/lslsetup-win95.exe` — contained the broken parser from before the fix.

---

## 1. The gap, concretely

`src/lslfiles.rs` embeds 36 files into `FIRSTBOOT_TOOLKIT`, and the nofmt
installer writes the stick's `/cdrom/bin`, `/cdrom/fuse` and `/cdrom/systemd`
from **that array alone**:

```rust
("bin\\lsl-pin-favorites", include_str!("../../../bin/lsl-pin-favorites")),
```

The source file had been fixed (`parse_gsettings_array` splits `gsettings`
arrays on commas). The binaries had not:

```
$ strings target/debug/lslsetup.exe | grep -c 'parse_gsettings_array'
0
$ strings target/debug/lslsetup.exe | grep -c 'strip brackets/quotes/commas'
1          # <- the OLD comment, i.e. the OLD parser
```

Same for `target/i586-rust9x-windows-msvc/debug/lslsetup.exe`,
`.../release/lslsetup.exe` and `dist/lslsetup-win95.exe`.

So a stick built from any of them would ship the old script and reproduce the
original symptom (all pinned apps, kitty included, absent from the panel) even
though the fix was committed.

## 2. Why the existing guards did not catch it

The repo already has a strong guard for the **z0 layer** (`WHYFAIL10`):
`assets/z0_sources.sha256` is regenerated by `misc/build-z0.sh`, and
`build.rs` re-hashes every listed source against the committed blob, failing
the build on drift. It works because the z0 layer is a *blob* — cargo tracks
the blob, not the sources packed into it, so the gap is real and had to be
closed by hand.

`FIRSTBOOT_TOOLKIT` is a **different shape**, and the difference is the trap:

| | z0 layer | firstboot toolkit |
|---|---|---|
| embedding | `include_bytes!` of a packed blob | `include_str!` of each source |
| cargo dependency | on the blob only | on every source file |
| stale on rebuild? | yes | **no** |
| stale in a prebuilt exe? | yes | **yes** |
| guard | `z0_sources.sha256` + build.rs | **none** |

Because `include_str!` gives cargo a dependency edge, "edit the file and
rebuild" *does* work — so the invariant looked self-enforcing. What it does not
cover is the binary that already exists and is not rebuilt: cargo is not asked,
the build succeeds, and the exe quietly keeps the bytes it was compiled with.
The fix was invisible for exactly one step — *rebuild the exe* — and nothing
reported that the step was outstanding.

## 3. Fix

Mirror the z0 guard for the toolkit.

1. **`misc/build-toolkit-manifest.sh`** — scans
   `static FIRSTBOOT_TOOLKIT` for its `include_str!` literals and writes
   `assets/toolkit_sources.sha256` (36 entries), the same format
   `build-z0.sh` uses.
2. **`rust9x/lslsetup/build.rs`** — a new freshness block (beside the z0 one)
   re-hashes every listed source and **fails the build** naming the drifted
   files, with the remedy in the message ("regenerate … then rebuild the exe").
3. **`misc/check-toolkit-freshness.sh`** — the by-hand/CI counterpart. It also
   asserts the manifest *covers* every embedded source, so a newly added
   `include_str!` cannot silently skip the guard.
4. **`build.sh`** and **`.github/workflows/ci.yml`** — run the checker before
   packaging / on CI, next to the z0 check.
5. **`src/lslfiles.rs` test** `toolkit_manifest_covers_every_embedded_source` —
   keeps the manifest and the embedded list in sync at test time.

CRLF discipline: `build.rs`, `lslfiles.rs` and `ci.yml` are CRLF files; the
inserted Rust string-continuations use `\` + CR + LF (a bare `\r\n` escape
would have changed the literals). Verified: 0 bare LF, byte counts balanced.

### Verified

```
$ bash misc/check-toolkit-freshness.sh
OK: embedded firstboot toolkit is fresh (36 sources verified)

# drift is caught, and named
$ echo '# probe' >> bin/lsl-pin-favorites && bash misc/check-toolkit-freshness.sh
DRIFTED:   bin/lsl-pin-favorites
STALE embedded firstboot toolkit: 1 source(s) differ from the manifest.
  Regenerate: bash misc/build-toolkit-manifest.sh
  Then REBUILD the exe - a stale exe writes the old content to the stick.
(exit 1)

$ bash tests/lsl-common.tests.sh        # 78 passed, 0 failed
$ bash misc/check-z0-freshness.sh       # OK, 19 files
$ python3 -c 'import yaml;yaml.safe_load(open(".github/workflows/ci.yml"))'   # OK
```

The manifest entry now pins the fixed script:

```
941588cdfaf031b917a23aff750f3847d3cc56aa398f4b2c546418002bfc7a0c  bin/lsl-pin-favorites
```

## 4. Still outstanding (unchanged from WHYFAIL13 §7)

**The exe has not been rebuilt.** This box is plain Linux (`Linux 6.14.0-37`),
the only toolchain is the Windows `rust9x` PE32+ one, and there is no `wine`
(and no Linux `cargo`), so `cargo +rust9x build` cannot run here — the same
blocker recorded in WHYFAIL13 §7. From a Windows host:

```
cd rust9x/lslsetup
cargo +rust9x build --target i586-rust9x-windows-msvc
```

Until that runs, the *built artifacts* still embed the old script. What has
changed is that this is now **detected** rather than silent: the build fails if
a toolkit source drifts from the manifest, and `build.sh`/CI fail if the
manifest does not match the tree.

## The rule worth keeping

> **`include_str!` protects the rebuild, not the artifact.**
> A source-embedded file makes "edit and rebuild" correct and makes "ship the
> binary you built last week" silently wrong. The dependency edge cargo sees is
> not the same as the guarantee a release needs: the release must be able to
> say *which* revision its bytes came from. Pin the bytes, not the path.
